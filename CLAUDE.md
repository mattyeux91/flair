# Flair — simulation de monde persistant football

## Pitch

Un monde persistant de football qui vit avec ou sans joueur humain (façon Football Manager × Dwarf Fortress × Hattrick), simulé par un **noyau pur, déterministe**. Le client de jeu incarne un **agent de joueurs** (scouter, placer, négocier, gérer une carrière) — c'est la seule boucle de jeu humaine, et elle n'est pas encore validée.

Ce fichier est un **index et un aide-mémoire des règles chères à violer par accident**. Il ne remplace pas `docs/` : en cas de doute sur une formule, un exemple de code ou un détail, lire le document source plutôt que deviner.

## Règles non négociables

- **Le noyau est une fonction pure, déterministe, zéro I/O** : `step(WorldState, TickContext): StepResult`. Aucun `rand()`/`mt_rand()`/`random_int()`, `time()`/`new DateTime()` sans argument, `getenv()`, accès disque ou réseau dans `kernel`. (`11-` §1, §9)
- **ECS strict, aucun sous-type.** `Player`, `Club`, `City` n'existent **pas** comme classes. Une entité est un entier ; « joueur » est le nom informel d'une entité qui porte des composants de compétences + `Contract` + `Fitness`. Les composants sont `readonly`, en lecture seule hors de leur système propriétaire. (`12-` §1, §2)
- **Vérité cachée vs perception.** `PlayerPhysicalSkills`/`PlayerTechnicalSkills`/`PlayerMentalSkills`/`PlayerPotentials` (la vérité) ne sont jamais exposés à un client. Ce qu'un observateur croit est **dérivé** à la lecture (bruit déterministe, fonction de `observerId`/`subjectId`/`observationCount`), jamais stocké. (`12-` §4)
- **Trois messages, jamais confondus** : Fait (passé, journalisé) / DecisionRequest (question transitoire, jamais journalisée) / Intent (futur immédiat, humain et PNJ via la même interface `IntentSource`). (`11-` §3, `16-` §1)
- **Un événement n'est jamais traité dans le tick qui l'a produit.** Il part en OutQueue vers le tick suivant. C'est ce qui rend les cascades impossibles à boucler dans un même tick — structurel, pas une limite de profondeur. (`13-` §2, `16-` §3)
- **Un système n'appelle jamais un autre système**, directement ou indirectement. Il émet un événement ou écrit un composant lu plus loin dans le pipeline. Ça n'interdit **pas** les fonctions pures partagées (`Football\Support\`, sans état ni RNG ni accès au monde) : deux appelants d'une même formule ne se commandent pas l'un l'autre. Critère d'extraction : **deux consommateurs réels, jamais un seul, jamais par anticipation**. (`13-` §2, `11-` §9)
- **Seuils d'émission** : une mutation de composant n'est pas un événement. Un fait mérite d'être émis s'il franchit un seuil comportemental, est irréversible, ou est racontable — sinon le système se tait. (`16-` §2)
- **Itération toujours triée par `EntityId` croissant.** Jamais l'ordre d'une `Map`/d'un `Set`. Idem pour l'OutQueue et le Scheduler : ordre total imposé, jamais l'ordre d'insertion. (`12-` §2, `13-` §4.2/4.5)
- **PRNG 32 bits obligatoire.** PHP bascule silencieusement un dépassement d'`int` en `float` : un PRNG 64 bits naïf casse le déterminisme sans erreur. PCG32/xoshiro128\*\*, masquage `& 0xFFFFFFFF` après chaque opération. Un flux dérivé par `(worldSeed, tick, systemId, entityId)` — jamais un PRNG global partagé. (`11-` §6, `13-` §4.1/4.3)
- **Les singletons sont adressés par type, une instance unique** (`MarketInflation`, `SeasonPhase`, `WorldClock`). Une donnée qui varie par pays/région (`EconomicClimate`, `Weather`) est un **composant** d'entité, pas un singleton. (`12-` §3 bis — corrigé le 2026-07-31, cf. note dans le doc)
- **Règles paramétriques dans le `Ruleset` versionné** (JSON, schéma validé), jamais codées en dur. Un monde est épinglé à `(kernelVersion, rulesetVersion)` ; changer les règles d'un monde vivant est une migration explicite, pas un hot reload. (`12-` §6, `13-` §6)
- **Graphe de dépendances du monorepo**, à faire respecter mécaniquement (`deptrac`/`phparkitect`) dès que le code existe :
  ```
  kernel   → (rien)
  ruleset  → (rien)
  worldgen → kernel, ruleset
  host     → kernel, ruleset, worldgen
  api      → host
  harness  → kernel, ruleset, worldgen
  admin    → api
  game-web → api (HTTP uniquement)
  ```
  Si `kernel` importe quoi que ce soit d'autre, le build casse. (`11-` §7)

## Stack et conventions

- **PHP 8.3+** partout (kernel/host/api). Pas de Rust, pas de Node pour le noyau — le CPU n'est pas le facteur limitant (`13-` §7, `11-` §6).
- **PostgreSQL seul.** Pas de Redis/Kafka/Mongo. `jsonb` pour les événements, tables classiques pour les projections.
- **Aucun ORM dans `kernel`.** Doctrine autorisé uniquement côté projections/API.
- **Symfony ou Laravel** pour `host`/`api`/`admin` — **jamais** dans `kernel`, qui doit rester exécutable dans un test unitaire nu.
- **SSE**, pas WebSocket, pour le flux temps réel.
- Namespace racine `Flair\`, PSR-4, PSR-12. **PHPStan niveau max obligatoire sur `kernel`.**
- Monorepo Composer (path repositories) : `packages/{kernel,ruleset,worldgen,host,api,admin,game-web,harness}/`. Pas encore créé — voir « Où en est le projet ».

## Où en est le projet

**Stade actuel : Phases 0, 1, 2 closes, et Phase 3 (Persistance et temps réel) — **son critère de sortie est atteint** le 2026-08-08 (`15-roadmap.md` §4). Trois lots : sérialisation du `WorldState`, extraction de `packages/worldgen`, puis `packages/host` (un monde vit en base).** La seconde moitié du critère de sortie de la Phase 2 a dû être *réécrite* avant d'être cochée : voir la note ⚠️ dans `15-` §4 Phase 2. Phase 0 vérifiée empiriquement le 2026-08-02 via `packages/harness/bin/aggregate.php` (40 saisons, seeds 42 et 7, 500 joueurs/18 clubs) : effectif stationnaire ~313-329 dès l'année ~13, répartition domicile/nul/extérieur 41.8/29.6/28.6% (proche du réel), 11 champions différents sur 18 clubs en 19 saisons (deux clubs à 4 titres chacun, aucun quasi-monopole). La fenêtre "20 saisons" du critère initial était trop courte pour une population de départ pas encore à l'équilibre d'âge — voir la note empirique dans `15-roadmap.md` §4. Phase 1 vérifiée le même jour : comparaison à graines appariées complète (baseline + `--set` + delta Gini/rotation) en ~1min49s, sous la barre des 5 minutes du critère de sortie ; Gini des titres et métriques de graphe d'événements, test de déterminisme état+séquence d'événements, et CI (`kernel` puis `harness`) tous en place. En parallèle, le prototype papier/CLI de la boucle de jeu de l'agent (`prototype/agent-loop/`) a confirmé que la tension commission/satisfaction/réputation est un vrai dilemme — conservé tel quel, en l'état de prototype jetable, pas promu en doc ni supprimé.

**Phase 2, avancement (`15-` §4, critère de sortie double : conservation monétaire + inflation dans la cible)** : le grand livre monétaire est posé — `Finances`/`Contract`/`SeasonIncome`, singleton `MonetaryMass`, `Football\FinanceSystem` (revenus de fin de saison répartis entre part égale et part au mérite via `meritShare`, salaires hebdomadaires, entretien et investissement en installations). `Football\FacilitiesSystem` referme la boucle « résultats → revenus → installations → entraînement/intake → compétences → résultats » (`docs/14-` §7). L'entretien des installations est **convexe** (coût ∝ carré de la qualité, pas linéaire) depuis le 2026-08-02 : c'est l'amortisseur mécanique de cette boucle, retenu à la place d'un mécanisme endogène type conseil d'administration/limogeage (hors périmètre Phase 2, pas de gouvernance de club) — mesuré sur graines appariées, Gini des titres 0.497→0.363 (défaut) et 0.717→0.628 (`meritShare=0.6`). Moitié « conservation monétaire » du critère de sortie mécanisée par `Harness\Tests\Regression\MonetaryConservationTest` (verte sur 20 saisons, cas plat et cas au mérite). `Contract` porte désormais `expiresOn`, et le couple `Football\ContractSystem`/`Football\SquadSystem` fait vivre le mercato annuel : expiration, renouvellement au prix du marché (`Football\Support\WageModel`, premier vrai prix du monde — `base × clamp(qualité/référence, 0.4, 2.5)`), et joueurs sans club repris par les clubs en déficit. Aucune indemnité de transfert (hors périmètre), donc aucun argent ne change de mains et la conservation monétaire reste vraie sans y toucher. Mesuré le 2026-08-02 sur six graines appariées : **rotation du top 5 de 47,8 % à 53,3 %, sur 6 graines sur 6** ; **Gini des titres sans effet détectable** (0,528 → 0,557, très en dessous de la dispersion entre graines 0,363-0,614 — un Gini lu sur une seule graine est du bruit). Un plancher d'effectif essayé pour corriger le fait que `MatchSystem` note la *moyenne* d'un effectif quand le budget en contraint le *total* s'est mesuré nuisible (rotation retombée à 49,2 %) et a été retiré ; la vraie correction appartient au moteur de match.

**Ordre des lots restants, révisé le 2026-08-04 (`15-` §4 Phase 2 pour le raisonnement complet)** — deux lots faits, **un seul restant** (le 3) :
1. ~~Les onze meilleurs dans `MatchSystem`~~ — **absorbé par le lot des postes, fait le 2026-08-04.** Il ne tenait pas debout séparément : la sélection d'un onze fondée sur un agrégat aveugle aux postes aurait été réécrite intégralement par le lot suivant. **Lot des postes livré** : `Position` (GK/DEF/MID/ATT), `Football\Support\PositionModel` (matrice de contribution façon Hattrick, source de vérité unique des poids), `Ruleset\PositionBalance`, un potentiel qui plafonne une **composition** et non chaque compétence, le onze composé par poste dans `MatchSystem`, `WageModel::quality()` devenue « note au meilleur poste », conscience minimale des postes dans `ContractSystem` et `YouthIntakeSystem`. Mesures : écart-type des attributs dans un même joueur 4,0 → 16,7 ; dans le profil d'un poste 1,5 → 8,6 ; club-années sans gardien 7,87 % → 1,39 %. Campagne à 6 graines appariées : **aucun effet sur l'équilibre** (Gini des titres et rotation du top 5 tous deux à 3 hausses / 3 baisses — c'est le résultat enregistré *avant* l'implémentation), victoires à domicile 42,6 % → 42,0 %, population stable, et **aucun recalibrage de `strengthScale`**. Limites assumées : le poste dérivé coïncide avec l'archétype dans 100 % des cas, une seule formation, aucune tactique, et 1,39 % de club-années sans gardien que seul le marché des transferts fermera.
2. ~~**Perception/scouting**~~ — **fait le 2026-08-05.** `ContractSystem` ne lit plus la vérité cachée : toutes ses décisions passent par une qualité **perçue** par le scout que le club emploie, et un club sans recruteur est le **pire** observateur du monde, jamais un omniscient. Livré : `Employment` + `Scout` (premier rôle non-joueur du monde, `observerId` est bien une **personne**), `Ruleset\PerceptionBalance`, `Football\Support\PerceptionModel` (pure, Irwin-Hall plutôt que Box-Muller — aucune transcendante de plus), `Contract::$signedOn` (porte `observationCount` sans structure par paire), `Core\SystemContext::stableHash()` (dérivation **invariante par tick**, sans `systemId`, pour que le futur marché perçoive un joueur comme le système de contrats). Aucun mécanisme d'observation, aucun rôle autre que scout, aucune embauche — Phase 5 / gouvernance de club. Trois écarts au plan, tous documentés : la formule de σ diffère de l'esquisse de `docs/12-` §4 (dans l'esquisse, un jugement de scout n'aide *pas* sur un joueur jamais observé — l'inverse du métier) ; le **poste** reste lu sur la vérité ; et la corrélation jugement ↔ classement n'est pas calculée, seulement affichée à côté du classement. Mesuré sur 6 graines appariées (perception contre `--set baseErrorPoints=0`) : **aucun effet sur l'équilibre compétitif** — Gini des titres et rotation du top 5 tous deux à 3 hausses / 3 baisses. La prédiction écrite avant l'implémentation (« hausse du Gini, handicap permanent ») était **fausse** : elle semblait confirmée sur la seule graine 42 (0,446 → 0,509), c'est le même piège du Gini mono-graine qu'au lot des contrats. Seul effet consistant : **masse salariale +0,54 %, 5 graines sur 6** — la malédiction du vainqueur, gratuitement (un club signe les joueurs qu'il surestime, donc la population sous contrat est biaisée vers les surévalués). Faible en amplitude, mais c'est le mécanisme que le lot marché va amplifier. Expérience de contrôle `--scout-judgement-spread=0` (tous les recruteurs égaux, comparaison appariée elle aussi) : **la hiérarchie de staff ne produit pas davantage d'effet mesurable** — Gini 4/6, champions distincts 3/6, indistinguables du hasard. Autrement dit `baseErrorPoints = 10` place le monde dans un régime où **la perception change les prix, pas les classements** ; pour qu'elle compte davantage il faudrait monter l'amplitude, ou rendre le jugement **endogène** (club riche → meilleur recruteur), ce qui est la gouvernance de club et donc hors Phase 2. Coût CPU +2 % (72,5 s → 74,0 s sur 40 saisons). **Fait de méthode à retenir : aucun lot qui ajoute une entité au genesis ne peut être une réduction bit-à-bit d'un monde antérieur** — les 18 scouts consomment 18 `EntityId`, ce qui décale l'allocateur pour toutes les entités créées ensuite à l'exécution, donc leurs flux RNG ; vérifié en faisant consommer les mêmes identifiants à un arbre pré-lot, qui redevient alors identique au chiffre près. Une comparaison à graines appariées se fait toujours **dans un même build**, jamais contre des nombres notés dans un document — y compris ceux-ci.
3. **Marché des transferts et inflation, un seul lot** (`docs/14-` §5) : indemnités, valorisation sur qualité **perçue**, négociation multi-tours, agents PNJ, `marketInflationTarget` et son régulateur. La moitié « inflation dans la cible » du critère de sortie **ne peut pas** être un lot séparé : le seul prix du monde étant `base × clamp(...)` avec `base` constante du `Ruleset`, l'inflation vaut identiquement zéro par construction et un régulateur ne régulerait rien tant qu'aucun argent ne poursuit un actif rare. Les indemnités rendent aussi `MonetaryConservationTest` non trivial pour la première fois.

   **En cours, découpé en 5 points suivis dans `docs/17-marche-transferts.md` — 4/5 au 2026-08-07, un commit par point.** Faits : (1) `Football\Support\MarketValueModel`, la valorisation pure ; (2) `Football\TransferSystem` + composant `Negotiation`, la négociation multi-tours en PNJ seul — **premier état multi-tick du noyau** (même composant dans `creates()` et `writes()`, cf. `SystemAccess::requiresCreatedEntity()`), mesuré à médiane 2 tours donc le risque « converge instantanément » de `docs/14-` §5 est écarté, avec la réserve honnête que 44,9 % se résolvent quand même au tour 1 ; point 2 réouvert pour `BoardPatience`, la patience individuelle du club vendeur ; (3) `Football\Intents\` — les décisions de l'acheteur passent par `BuyerIntentSource`, dont `NpcBuyerIntentSource` et `SubmittedBuyerIntentSource` sont deux implémentations. Écart tranché : interface **de domaine**, pas le `Core\IntentSource` + `WorldView` générique de l'esquisse de `docs/11-` §3, qui aurait été une abstraction posée par anticipation avec un seul consommateur. Le vrai contenu du point 3 n'était pas l'interface mais le **découpage en ticks** : la contre-demande est posée au tick N et la réponse lue au N+1, sans quoi un humain répondrait à une question qu'il n'a pas encore vue — re-mesure identique au chiffre près (715 négociations, médiane 2, moyenne 2,81, 44,9 %), le refactor est neutre en comportement ; (4) **les indemnités se paient**. Le design n'avait aucune latitude : « un seul writer par composant » désigne `FinanceSystem` pour `Finances`/`MonetaryMass` et `SquadSystem` pour `Contract`/`SquadMembership`, donc `TransferSystem` décide en queue de pipeline et les deux appliquent au tick suivant — `TransferAgreed` devient exécutoire, `ContractSigned` (émis en même temps) déplace le joueur. Une indemnité **n'est ni une injection ni un puits** : `MonetaryMass` ne bouge pas, ce qui rend `MonetaryConservationTest` non trivial pour la première fois (garde-fou ajouté : le test exige qu'il ait réellement circulé des indemnités). Pas de Fait `TransferCompleted`, il n'aurait rien ajouté aux deux autres. Solvabilité ajoutée comme **politique de PNJ** (le plafond est borné par le solde), pas comme règle du système. Mesuré sur deux graines : négociations 715 → 590, part au premier tour 44,9 % → 39,7 % (la réserve du point 2 s'améliore toute seule), et surtout **le marché ne concentre rien** — aucun solde négatif, Gini des soldes de club 0,011/0,008, indemnités totales marginales devant la masse en circulation. Le marché est réel mais **économiquement inerte**, parce que le PNJ maximise `qualité/prix` donc chasse les fins de contrat que `MarketValueModel` brade (indemnité médiane à 9 % de `baseValueCents`). C'est le cadrage du point 5 ; (5) **`indice_inflation_global` et sa régulation**, le point qui a le plus dévié de sa conception. Trois mesures ont interdit la forme prévue : ~3 transferts par saison rendent **aucun indice de prix calculable** ; la masse monétaire est négative neuf saisons puis **traverse zéro**, donc inutilisable en dénominateur ; et surtout **le monde n'a aucune inflation endogène** (sans régulateur, masse et masse salariale plates trente saisons — salaires et valeurs sont des formules du `Ruleset`, pas des prix d'équilibre). L'indice est donc posé comme une **décision de politique monétaire** qui multiplie *tout* ce qui est nominal, et le taux réalisé égale la cible **par construction**. L'asservissement des injections a été **construit, mesuré instable deux fois, retiré** (dénominateur endogène qui bouge dans le mauvais sens) au profit d'une boucle ouverte : indice + terme d'anticipation `cible × masse`. `Football\Singletons\MarketInflation` (second singleton), `Ruleset\InflationBalance`, `ClubInvestedInFacilities` gagne `referenceCents` parce que `FacilitiesSystem` **ne peut pas** lire l'indice (cycle dans `SystemGraph`). **Défaut à `0.0`, no-op strict vérifié au centime** ; à 3 % le monde reste stable mais le chômage tombe de ~35 à ~2 — mesuré, non corrigé, d'où le défaut à zéro. Piège PHP à retenir : `(int) round(PHP_INT_MAX * 1.0)` rend un entier **négatif**, et le `min`/`max` naïf n'y échappe pas (`(float) PHP_INT_MAX` vaut 2⁶³) — `FinanceSystem::scaled()` clampe par comparaisons explicites.

**Phase 3, avancement (`15-` §4)** — **lot 1 fait le 2026-08-08 : le `WorldState` se sérialise.** `Core\Snapshot\` dans le kernel (pur, zéro I/O : le format appartient au noyau, le Host ne stockera que des octets) — `TypeRegistry` (clé stable ↔ classe, **aucun FQCN dans le payload**, et le même registre alimentera `events.type`), `SnapshotCodec`, `ValueCodec` réflexif, `SnapshotContract`, l'attribut `SnapshotArrayOf`, l'enveloppe `WorldSnapshot`, `JsonSnapshotFormat`, plus `Kernel::VERSION` et `Football\FootballTypes`. Trois corrections apportées à la conception écrite : **le tick n'est pas dans le `WorldState`** (`13-` §8 écrivait `$state->tick + 1`, qui n'existe pas — il vit dans `TickContext`, d'où l'enveloppe) ; **le rejeu du delta est abandonné** au profit d'un snapshot par tick dans la transaction des événements (mesuré 500 joueurs/18 clubs/12 saisons : 0,38 Mo par snapshot, 6,9 ms pour encoder, 13,7 ms pour relire, contre 6,1 ms de coût moyen d'un tick — à 1 tick/h rejouer n'achète rien et rouvre le piège du `13-` §6) ; et **la conformité est mécanisée** (`SnapshotConformanceTest` balaie le disque et exige que tout type du domaine soit enregistré **ou atteignable** depuis un type enregistré — une liste à la main aurait eu le défaut qu'on corrigeait). Le critère de sortie de la phase est déjà sous test **sans base de données** : `Harness\Tests\Regression\SnapshotContinuityTest` interrompt un run au premier tick où l'OutQueue, le Scheduler puis une `Negotiation` sont réellement occupés, ne garde que la chaîne JSON, et exige une suite indiscernable — même hash d'état **et** même hash d'événements, avec échec si l'une des trois structures n'a jamais été couverte. Éprouvé par trois sabotages du codec, tous détectés. Trou fermé au passage : `WorldHasher` tenait sa propre liste de types, sans `BoardPatience`, `Negotiation` ni `MarketInflation` — **tout le marché des transferts était hors du test de déterminisme depuis le lot 3** ; elle dérive maintenant de `FootballTypes`. Non-régression vérifiée dans un même build (autoloader pointant tour à tour sur l'arbre pré-lot et l'arbre courant) : état et séquence d'événements **identiques au chiffre près**. **Lot 2 fait le 2026-08-08 : `packages/worldgen`.** Un déblocage, pas une fonctionnalité — `host` doit pouvoir créer un monde et le graphe de `11-` §7 lui interdit d'importer `harness`. `WorldFactory` (ex-`PopulationFactory`), `ClubFactory`, `CompetitionFactory` et `StaffFactory` ont quitté `harness/src/Population/` ; `Worldgen\WorldSpec` porte la forme du monde, `Harness\Population\PopulationSpec` survit avec le seul `years` (une durée de run n'est pas une propriété du monde) et **garde sa signature à plat**, en gagnant un `world()` — les ~20 sites de construction n'ont pas bougé. Le seul critère de réussite d'un lot pareil est l'**exactitude bit-à-bit**, que les suites de tests ne peuvent pas prouver (elles comparent des runs entre eux dans un même build) : vérifié par empreinte, arbre pré-lot contre arbre courant — état, séquence d'événements, compteur d'entités et `EntityId` joueurs **identiques**. ⚠️ Règle d'or à ne jamais oublier dans `worldgen` : **l'ordre des tirages RNG et des allocations d'`EntityId` est une donnée d'architecture**, le réordonner change le monde entier (cf. les 18 scouts du lot perception) — trois précautions du code portent cette contrainte, détaillées dans `packages/worldgen/README.md`.

**Lot 3 fait le 2026-08-08 : `packages/host`, et le critère de sortie de la Phase 3 est atteint.** Trois tables (`worlds`, `events`, `snapshots`), `AdvanceWorld`/`CreateWorld`, verrou `pg_try_advisory_xact_lock`, CLI `bin/host.php`, PostgreSQL en conteneur (`docker-compose.yml`, port **54329** pour ne pas heurter le postgres local de la machine). **Stack : `illuminate/database` seul, pas de skeleton Laravel** — `api → host` fait de `host` une *dépendance*, et deux skeletons d'application ne se composent pas ; Laravel complet ira dans `api` en Phase 4. Le CLI est un script nu (idiome `harness/bin/*.php`) ; `symfony/console` s'ajoutera s'il dépasse ~8 commandes, c'est la couche sur laquelle Artisan lui-même est bâti.

**Tout tient dans une seule transaction** — verrou, lecture du snapshot, `step()`, Faits, snapshot, tick. C'est cette atomicité seule qui rend le critère vrai. `Host\Tests\CrashRecoveryTest` le vérifie au sens littéral (sous-processus réel, **SIGKILL** en plein vol, trois fois), avec deux assertions : base cohérente, **et** monde repris identique à un monde jamais interrompu. Sabotage : sans transaction, détecté 4/4 ; avec deux transactions successives, 2/6 — filet probabiliste assumé, la garantie est structurelle.

⚠️ **Trois pièges mesurés, à ne pas réapprendre.** (1) **Le coût d'écriture en base ≈ le coût du noyau** : 17,8 ms/tick contre 18,7 ms de simulation (500 joueurs/18 clubs) — première confirmation chiffrée de `13-` §7. (2) **`jsonb` réordonne les clés d'objet** : un snapshot relu depuis `jsonb` n'est plus identique octet pour octet à ce que le noyau a produit ; `snapshots.state` est donc en **`json`**, `events.payload` reste en `jsonb` (les projections devront l'interroger). (3) **Le verrou advisory survit 0,7 à 3,4 ms au processus tué** — sans conséquence pour un cron horaire, fatal pour un test qui enchaîne kill et reprise immédiate.

Restent (Phase 4 en réalité) : projections et SSE. Le jour venu, **les projections rejoindront cette même transaction** et **la diffusion SSE restera dehors** — publier avant le commit annoncerait un tick qui peut encore être annulé.

Ce qui existe et tourne de bout en bout — **détail classe par classe dans `packages/kernel/README.md`, pas dupliqué ici** :
- Le socle générique (`src/Core/` : ECS, messagerie Fait/DecisionRequest/Intent, `Scheduler`/`OutQueue`, `Pipeline`, PRNG 32 bits, `Ruleset` versionné imbriqué par sous-domaine, `Simulation::step()`, sérialisation `Snapshot/`).
- Le domaine football (`src/Football/`) : vieillissement (retraite + progression des compétences), entraînement, intake de jeunes (ferme la boucle démographique), calendrier + match L0 (Dixon-Coles) + classement, grand livre monétaire + installations + contrats + perception (Phase 2, ci-dessus). Aucun système n'écrit `Employment`/`Scout` : le staff est semé au genesis, comme `Facilities`/`Finances`.
- Pipeline : déclaré une seule fois dans `Football\FootballPipeline` (`bin/demo.php`, harness et futur `host` le lisent), et **son ordre d'exécution est dérivé** des déclarations `reads()`/`writes()`/`removes()` par `Core\Pipeline\SystemGraph` — tri topologique, ex æquo départagés de façon stable par la liste déclarée, jamais par le nom. Ordre obtenu : `FacilitiesSystem`, `SquadSystem`, `TrainingSystem`, `RetirementSystem`, `FinanceSystem`, `PlayerDevelopmentSystem`, `YouthIntakeSystem`, `CalendarSystem`, `MatchSystem`, `CompetitionSystem`, `ContractSystem` (`YouthIntakeSystem` est descendu de la 1re a la 6e place le 2026-08-04, quand il s'est mis a lire l'effectif en place pour savoir quel poste manque au club — l'ordre s'est re-derive seul, personne n'a arbitre). `SquadSystem` (application) et `ContractSystem` (décision) encadrent tout le reste : le décideur doit lire les compétences et `Finances`, donc passer après leurs writers ; l'applicateur doit écrire `SquadMembership` avant `TrainingSystem`/`MatchSystem`. ⚠️ Ces deux contraintes **sont** satisfaites simultanément et le graphe de dépendances est acyclique — contrairement à ce que ce paragraphe affirmait avant le 2026-08-03. La vraie contrainte, elle bien réelle, est que l'*effet* d'une décision ne peut pas s'appliquer dans le tick qui l'a prise : d'où décider tard, émettre un Fait, appliquer tôt au tick suivant.

Décision à connaître avant de toucher au moteur de match : `exp()` est la première fonction transcendante autorisée dans le noyau (une seule machine exécute le noyau, donc pas de risque de portabilité cross-plateforme — cf. `docs/13-` §4.8 et `packages/kernel/README.md`). `PlayerFactory` reste volontairement sans fonction transcendante (`Beta(1,k)` plutôt qu'une log-normale) pour un besoin différent, la portabilité cross-plateforme de la loi de talent — à revisiter si une comparaison de hash inter-machines apparaît un jour. `PerceptionModel` suit le même arbitrage que `PlayerFactory` (Irwin-Hall plutôt que Box-Muller) : ni `log` ni `cos`, seulement `sqrt`, algébrique et exactement spécifiée par IEEE-754.
